### <a name="_3bfxc9a45514"></a>**Контекст**
- Основной трафик приходится на поиск и бронирование жилья
- Около 1 млн пользователей

### <a name="_3bfxc9a45514"></a>**Причина**
Каким будет оптимальный план миграции на архитектуру To-be, учитывая:
- Контекст
- Поэтапный переход к микросервисной архитектуре, применяя паттерн Strangler Fig

### <a name="_qmphm5d6rvi3"></a>**Решение**
1.	API Gateway + Hotel Service
    - логика IsHotelFullyBooked в монолите Booking Service
    - ACL с репликой из HotelService для BookingService

    - ACL взаимодействует с монолитом синхронно gRPC
    - ACL актуализирует реплику асинхронно через шину

2.	Review Service
    - ACL с репликой из ReviewService для BookingService

    - ACL взаимодействует с монолитом синхронно gRPC
    - ACL актуализирует реплику асинхронно через шину

3.	User Service
    - ACL с репликой из UserService для BookingService

    - ACL взаимодействует с монолитом синхронно gRPC
    - ACL актуализирует реплику асинхронно через шину

4.	Promocode Service
    - Логика применимости промокода в Booking Service
    - ACL с репликой из PromocodeService для BookingService
    - Зависимости от User Service нет

    - ACL взаимодействует с монолитом синхронно gRPC
    - ACL актуализирует реплику асинхронно через шину

5.	Booking Service
    - отключение от ACL
    - перенос реплик в Booking Service

Преимущества
- Каждый этап миграции затрагивает 1 взаимосвязь
    - сниженный риск ошибки и сбоев
- Первым выделяется в микросервис Hotel Service
    - таким образом 2 цели основного трафика разделяются и общаются через асинхронное взаимодействие, их можно масштабировать отдельно. Что отразится на отзывчивость системы для пользователей на 2 главных функциях системы
- Можно разрабатывать новые фичи для поиска жилья после первой миграции

### <a name="_qmphm5d6rvi3"></a>**Цель**
- Инкрементность изменений
- Максимально быстрая адаптатция к нагрузкам
- Максимально быстрое повышение адаптивности системы в ее одной из главных функий

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Если начать миграцию с BookingService
- первая итерация займет существенно больше времени, так как сервис владеет максимум связей 
- существенно возрастает риск критических ошибок и длительных периодов недоступности приложения для пользователей изза их устранения
- существенно возрастает нагрузка на компетентность команды - первой окажется самая сложная миграция
- не будет преимуществ по масштабирования - микросервис будет связан синхронно с монолитом
- микросервис нельзя будет написать в to-be состоянии, так как еще нет шины сообщений и требуемого потока сообщений - его придется переписывать по итогу еще раз

**Недостатки, ограничения, риски**
- так как сервис бронирования по графику выносится самым последним, то в него дольше всего нельзя будет вносить новую функциональность
- нет метрик, доказывающих, что второй по уровню нагрузки - это компонент HotelService. Как следствие нельзя сказать, что вынос его в первую очередь отражает самым актуальным бизнес-требованиям.
